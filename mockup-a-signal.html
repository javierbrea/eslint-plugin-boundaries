How it works

Three steps from folder structure to enforced architecture

Everything lives in your existing ESLint config. No extra service, no new CLI, no build step.

STEP 1

Classify files and elements

Describe which folders are components, modules or helpers, and which files are tests, styles or stories. The plugin matches every file against your descriptors.

settings: {
  "boundaries/elements": [
    { type: "helper",    pattern: "helpers/*" },
    { type: "component", pattern: "components/*/*" },
    { type: "module",    pattern: "modules/*" },
  ],
  "boundaries/files": [
    { pattern: "**/*.spec.js", category: "test" },
  ],
}
STEP 2

Write dependency policies

Say who may import whom. Start with a default, then allow or disallow by element type, file category, module origin or the import kind itself.

"boundaries/dependencies": [2, {
  default: "disallow",
  policies: [
    { from: { element: { type: "component" } },
      allow: { to: { element: { type: "helper" } } } },
    { from: { element: { type: "module" } },
      allow: { to: { element: { types: ["component", "helper"] } } } },
    { disallow: { to: { file: { categories: "test" } } } },
  ],
}]
STEP 3

Get feedback where you code

Violations show up as ESLint errors in your editor and fail CI. Messages are templated, so they can explain the rule instead of just naming it.

src/helpers/format/index.js
  12:1  error  No rule allowing this dependency
         was found. File is of type 'helper'.
         Dependency is of type 'component'
         boundaries/dependencies

✖ 1 problem (1 error, 0 warnings)

Built for real codebases, not toy examples

One file, three perspectives

Every file is described along three independent layers at once: the architectural element it belongs to, its own file category, and where each imported module resolves from. Policies can combine any of them.

elementfilemoduledependency

Selectors that capture context

Match by type, by captured path fragments, by category or by origin. Reuse captured values from the from side in the to side, so "a component may only import its own sub-components" is one policy, not twenty.

Describe the same file from every angle

Hover a layer to see which part of the runtime description it produces. Policies read all of them, on both sides of the dependency.

elementThe architectural unit the file belongs to: component, service, module…
fileThe file's own categories, independent of its element: test, index, style…
moduleWhere a dependency resolves from: a local path, an external package, a core module.

In your editor

The violation, where it happens

A helper reaching into a component is wrong in this architecture. The policy says so, and the editor says so before the review does.

eslint.config.js
// helpers may only depend on other helpers
{ from: { element: { type: "helper" } },
  allow: { to: { element: { type: "helper" } } },
  message: "Helpers must stay independent from ${to.element.type}s" }
src/helpers/format/index.js
import { Price } from "../../components/Price";

export function formatPrice(value) {
  return <Price value={value} />;
}
