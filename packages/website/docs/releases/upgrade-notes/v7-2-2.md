# Upgrade Notes for v7.2.2

## Overview

Version 7.2.2 is a patch release (`eslint-plugin-boundaries` 7.2.2, `@boundaries/eslint-plugin` 7.2.2 and `@boundaries/elements` 3.1.3). It doesn't change the configuration format, but it fixes how some files are described. If your lint results depended on the previous, incorrect descriptions, they may change after upgrading.

Each section below explains what changed, who is affected, how to find the affected files, and how to adapt your configuration.

- **[Nested element paths](#nested-element-paths)** — the `path` and `fileInternalPath` of a nested element are now correct when its matched path also appears earlier in the file path.

## Nested element paths

Fixed in [#494](https://github.com/javierbrea/eslint-plugin-boundaries/issues/494).

### What changed

When a file matches an element descriptor, the plugin resolves the element `path` from the segments matched by the `pattern`, for example `components/Button`. Before v7.2.2, it searched the file path for those segments and used the **first occurrence**. When the same segments also appeared earlier in the file path, the element got the path of that earlier occurrence, and its `fileInternalPath` was computed from that wrong path.

The plugin now resolves the element `path` from the position where the pattern actually matched.

For example, with this configuration:

```js
"boundaries/elements": [
  { type: "component", pattern: "components/*", capture: ["name"] }
]
```

| File path | Description property | Before v7.2.2 | From v7.2.2 |
| --- | --- | --- | --- |
| `src/components/ButtonGroup/components/Button/Button.js` | `path` | `src/components/Button` | `src/components/ButtonGroup/components/Button` |
| | `fileInternalPath` | `src/components/ButtonGroup/components/Button/Button.js` | `Button.js` |
| `src/components/Button/components/Button/Button.js` | `path` | `src/components/Button` | `src/components/Button/components/Button` |
| | `fileInternalPath` | `components/Button/Button.js` | `Button.js` |
| | `parents` | none | the `component` element at `src/components/Button` |

The `types` and `captured` values of these elements were already correct.

### Who is affected

You are affected when both of the following are true:

- An element descriptor matches from the right side of the path, which is the default ([`partialMatch: true`](../../classification/elements.md#partialmatch-optional)). Elements matched with `partialMatch: false` or with the deprecated `mode: "full"` already got the right `path`, but their [parent elements](../../classification/elements.md#hierarchical-elements) may be affected.
- The segments matched by the pattern also appear earlier in the file path. This usually happens with nested elements:
  - Whose folder name is a prefix of an ancestor folder name, such as `components/Button` inside `components/ButtonGroup/`.
  - With the same name as an ancestor, such as `components/Button` inside `components/Button/`.

  The earlier occurrence doesn't need to be an element: `legacy-components/Button/` also contains `components/Button`.

Before upgrading, you may have noticed these effects on the affected files:

- Policies, selectors and [custom message templates](../../policies/policies.mdx) using the element `path` or `fileInternalPath` got wrong values. For example, policies that only allow importing the main file of an element reported false errors, and policies that disallow specific internal files didn't apply.
- When a nested element had the same name as an ancestor, both got the same `path`. The nested element lost its parent, and dependencies between both elements were considered [internal](../../classification/dependency.md#element-relationship), so the [`dependencies`](../../rules/dependencies.md) rule skipped them unless `checkInternals` was enabled. Their relationships (`child`, `parent`, `descendant`, etc.) were also wrong.

### What to expect after upgrading

- The false errors in the affected files disappear.
- New errors may appear where the wrong descriptions were hiding real violations of your policies. Dependencies between a nested element and an ancestor with the same name are no longer internal, so they are now checked, and policies based on `path`, `fileInternalPath` or relationships now apply to the affected elements.

### How to find the affected files

1. List the files of nested elements and review the ones whose folder name is a prefix of, or equal to, an ancestor folder name. For example, for elements defined with `pattern: "components/*"`:

   ```bash
   find src -type f -path "*/components/*/components/*"
   ```

2. Compare the lint results before and after upgrading. Changes in the affected files are caused by this fix:

   ```bash
   npx eslint . --format json --output-file before.json
   # upgrade the plugin
   npx eslint . --format json --output-file after.json
   ```

3. To check the description of a specific file, lint it with [debug mode](../../guides/debugging.md) enabled. The element `path` must end with the folder matched by the pattern, and `fileInternalPath` must be relative to it:

   ```bash
   ESLINT_PLUGIN_BOUNDARIES_DEBUG=1 npx eslint src/components/ButtonGroup/components/Button/Button.js
   ```

### How to adapt your configuration

No configuration change is required: the descriptions now match what your configuration already defines.

- Remove the workarounds you added for the false errors, such as `eslint-disable` comments, additional policies, or broader `fileInternalPath` patterns.
- Fix the new errors, or adapt your policies if those dependencies should be allowed. For example, to allow a component to import the main file of its child components, including those with the same name:

  ```js
  {
    from: { element: { type: "component" } },
    allow: [
      {
        to: {
          element: {
            type: "component",
            fileInternalPath: "{{to.element.captured.name}}.js",
          },
        },
        dependency: { relationship: { to: "child" } },
      },
    ],
  }
  ```
