# Phase 10: the sanity suite of the website and the playground

Goal: a private Nx project, `test/website-e2e` (`website-e2e`), runs a sanity suite with Playwright in Chromium, at a desktop and a narrow viewport, against the built website. It reaches the page only through the page objects of phase 9 and those it adds, and CI runs it on every pull request.

Issue: #640, `closes #640`. Branch `test/640/website-e2e` from `feat/539/playground`; PR into `feat/539/playground`, title `test(website): check the website and the playground in Chromium`. Changelog: none (tests and CI). The PR description lists each spec with what it covers, and the acceptance criteria of #640 with how each one was checked.

Read first:

- Decision 22 of the index and issue #640.
- `test/browser-e2e` (`package.json`, `project.json`, `playwright.config.js`, `test/global-setup.js`, `eslint.config.js`, `AGENTS.md`, `README.md`): the model for the project, its targets and its docs.
- `.agents/rules/playwright-testing.md` and the `./playwright` entries of `playground` and `website`, from phase 9.
- `packages/website/scripts/screenshots.mjs`: the viewports (1440×900 and 390×844), the hosts whose errors are tolerated (`api.github.com`, `api.npmjs.org`) and the 404 path.
- `packages/website/src/pages/playground.tsx`, `src/components/OpenInPlayground/` and the `share` domain of the playground (`useShareLink` copies the link with `navigator.clipboard.writeText`).
- `.github/workflows/build.yml` (jobs `build`, `test-browsers` and `all-checks`), `publish.yml`, `publish-to-github.yml` and `.github/actions/install-browsers`.

Preconditions: phase 9 merged.

## Scope

In: the project, its fixtures and specs, the page objects the specs need (each beside its component, exported from its entry and mirrored from its jsdom sibling), CI, the spec sections of the rule and the docs of the project. Out: Firefox and WebKit, visual comparisons, the local app, and the detailed behavior of the playground, which stays in the jsdom specs.

## Steps

### Project

1. `test/website-e2e`, modelled on `test/browser-e2e`: `package.json` (private, `@boundaries/website-e2e`, with `website` and `@boundaries/playground` as `workspace:*`), `project.json`, `tsconfig.json`, `eslint.config.js`, `cspell.config.cjs`, `AGENTS.md`, `CLAUDE.md` (`@AGENTS.md`) and `README.md`. The specs are TypeScript, type-checked by `check:types`. `eslint.config.js` forbids, in every file of the project, the fixed waits that the Playwright files of `playground` and `website` forbid (`waitForTimeout`, `waitForSelector`, `waitForFunction` and the `networkidle` load state), and, in the specs, every method of a page that takes a selector or returns a locator (`locator`, the `getBy*` methods, `$` and the like), so that a locator lives only in a page object (#640).
2. `test:e2e` installs Chromium (`playwright install chromium`) and runs `playwright test`. Its `project.json` makes it depend on the `build` of `website` and on the `build:playwright` of `playground` and `website`, and makes `lint` and `check:types` depend on the same two `build:playwright`, since they resolve the imports of the two entries, as the `lint` and `check:types` of `website` depend on the playground's.
3. `playwright.config.ts`: Chromium only; a `desktop` project at 1440×900 and a `narrow` one at 390×844; a `webServer` that serves `packages/website/build` with `docusaurus serve` on a fixed port, without opening a browser; no retry locally, and one retry with a trace in CI. A spec that needs the panes runs only in `desktop`, skipped in `narrow` by a tag in its title and `grepInvert`, as the rule says.
4. Fixtures: `test` and `expect` extended with the root page objects, and a console listener that fails the test on an error, except for the requests to the hosts that `screenshots.mjs` tolerates.

### Specs

5. Website: from the home to the docs and the Quick start, through the navbar and the sidebar; `/this-page-does-not-exist/` shows the 404 page; none of those pages logs a console error or starts a web worker, which only `/playground/` does (#635).
6. Playground, `desktop`: `/playground/` without a hash loads the Quick start example (the tree lists its files, the problems panel its count, a file opens in the inspector); the example picker loads another example and changes the hash; Help opens, its link to the playground guide reaches `/docs/guides/playground/`, and it closes; Reset brings back the Quick start; a reload keeps the project on screen.
7. Open in playground, `desktop`: the button at the end of step 6 of the Quick start opens the playground with its project after a client-side navigation, and the same link visited directly opens the same project, not the one the store remembers.
8. Share, `desktop`: `page.addInitScript` replaces `navigator.clipboard.writeText` with a function that keeps the link; Share reads `Copied`, and the kept link, opened in a new page, shows the same project and config.
9. Narrow: `/playground/` shows the desktop-only note and never requests the chunk of the playground, recognized by a string that only the chunk holds (open point).
10. Each page object a spec needs is added beside its component and exported from its entry; in the playground it mirrors its jsdom sibling, and in the website it has none. The issue lists the website's: `OpenInPlayground`, the playground page (phase 9), the swizzled `NotFound`, `Footer` and `NavbarItem`, and the navbar and the docs sidebar, which Docusaurus renders and the site only configures (open point). The specs hold no locator or selector.

### CI

11. `.github/workflows/build.yml`: the `test-browsers` job runs `pnpm nx check:all website-e2e` after `browser-e2e`, and the `check:all` of the `build` job excludes `website-e2e` as it excludes `browser-e2e`. `all-checks` already needs `test-browsers`. `publish.yml` and `publish-to-github.yml` run `pnpm check:all` (`nx run-many -t check:all --all`), which now runs this suite too, after `install-browsers`, which installs Chromium with Firefox and WebKit. The `NOTE` comments of those steps and of the `check:all` of the `build` job name `browser-e2e` alone, and name both projects after this phase.

### Docs

12. `.agents/rules/playwright-testing.md`: `test/website-e2e/**` in its `paths`, which it leaves out until the project exists, and the sections on specs (only through page objects, the fixtures, the tags per project), determinism (no fixed wait; a test that passes only on retry is a defect to fix, never a reason for another retry, a longer timeout or a wait) and running the suite.
13. `test/website-e2e/AGENTS.md` and `README.md`: what the suite covers, how to run it and read a failure, and where a spec and a page object go. The `repo-architecture` skill lists the project and its dependencies.

## From phase 9 (#645)

- `@boundaries/playground/playwright` exports the base `Pom`, `PlaygroundPom`, `ShellPom` and `ShellLayoutPom`, and the types `PomOptions`, `PomChildOptions` and `PomSearchBase`; `website/playwright` exports `PlaygroundPagePom`, built as `dist-playwright/playwright.mjs` because `website` is not an ES module package. `.agents/rules/playwright-testing.md` says how a page object is added and what it imports.
- A page object is built with `{ page }` and builds its children with `childPom`; its `root` and `page` are protected, so no page object hands out a locator and no spec holds one (#640). A spec asserts a value that settles with `expect.poll` over a value getter, which is async and never waits, or calls a waiting method of the page object.
- `PlaygroundPom` has `shell` and `waitUntilLoaded()`, which polls the shell landmark named `Playground`. `PlaygroundPagePom` finds its root as the `main` landmark and has `playground`, `isNoteVisible`, `noteText`, `isLoadingBoxVisible`, `waitForNote()`, `waitUntilNoteHidden()` and `waitUntilLoadingBoxGone()`; the test ids of the note and the loading box are in `packages/website/src/pages/playground.constants.ts`.
- The `pages.exclude` of `docusaurus.config.ts` keeps `*.playwright.ts` and `*.constants.ts` files out of the routes.

## From the worker (#635)

- The playground evaluates in a web worker, so the verdicts arrive after the shell renders: a spec waits for them through a waiting method of a page object or with `expect.poll` over the status of the top bar or a verdict, never with a fixed wait. While an evaluation is late the status reads `evaluating…` (decision 23).

## Open points

- How the narrow spec recognizes the chunk of the playground. Default: by a string only the chunk holds, such as `ROOT_CLASS` (`jsb-play-root`, `packages/playground/src/ui-kit/helpers/theme/theme.constants.ts`), read from the bodies of the script responses; check first that no other script of the page holds it.
- The port of the `webServer`. Default: a fixed one other than 3000, so that a running `pnpm nx start website` never answers the suite.
- Where the page objects of the navbar and the docs sidebar go, which the site does not swizzle. Default: where a swizzle would put the component, `src/theme/Navbar/Navbar.pom.playwright.ts` and `src/theme/DocSidebar/DocSidebar.pom.playwright.ts`, with no `index` file. Docusaurus makes an alias of every file under `src/theme/` (`createAliasesForTheme` in `@docusaurus/core`), and only `<Component>.tsx` or `<Component>/index.tsx` replaces a component, so these files replace none; the `theme` element of the website's `eslint.config.mjs` already holds them.
- The guard of fixed waits, which the `eslint.config.mjs` of `playground` and `website` repeat word for word, and which this project would repeat a third time. Default: one export of `support/eslint-config/index.js` that the three configs use.
